# Generating valid local test data

How to fill a local DB with realistic, **invariant-valid** data for manual testing
(inventory timeline, in/out export, POs, etc.).

## Steps

```bash
docker compose up -d postgres pgweb        # 1. database (port 5432, UI 8081)
make migrate                               # 2. schema
make seed                                  # 3. base reference data
                                           #    (units, suppliers, products, inventories,
                                           #     menus, sale_orders, users)
# 4. transactional data (POs, ledger, receipts, submissions, …)
docker exec -i cim_postgres psql -U postgres -d cim_db -v ON_ERROR_STOP=1 \
  < test/data/local_seed.sql
```

`local_seed.sql` is **re-runnable** — it TRUNCATEs only the transactional tables and
rebuilds them; base reference data from `make seed` is left untouched.

## Why a separate SQL step

`make seed` only creates static reference data. Purchase orders, the inventory
**ledger** (`inventory_transactions`), receipts, etc. are generated by
`local_seed.sql`.

## Invariants the data must respect

The app enforces these (e.g. `InventoryItem.ValidateActivePurchaseTransactions`);
violating them does not crash but produces nonsensical numbers / breaks mutations:

1. **On-hand = lots remaining:** `inventory_items.quantity` ==
   `Σ(lot.quantity − lot.consumed_quantity)` over its `purchase`/`transfer_in` lots.
2. **Consumes are FIFO-linked:** every `sell`/`disposal`/`transfer_out` sets
   `counter_transaction_id` to its source purchase lot and increments that lot's
   `consumed_quantity`. A lot is never over-consumed.
3. **Positive margin:** purchase `unit_price` < selling price.
4. **Day cells need in-window purchases:** the export's daily "purchases in period"
   columns only fill from `purchase`/`transfer_in` txns **dated inside the window**.
   `local_seed.sql` scatters in-window purchase lots across recent days for this.
5. **No negative beginning stock:** each item gets a large opening lot dated before
   the window so beginning stock stays ≥ 0.

> Transfers (`transfer_in`/`transfer_out`) are intentionally **not** seeded — real
> transfers need cross-inventory lot pairing that should be created via the API,
> not raw SQL. The export's transfer columns will be zero.

## Built-in test case: selling-price change within a report

`local_seed.sql` seeds a deliberate price-change scenario (step 9b): for **products
1–5 in every inventory**, PO item "A" gets an **April** purchase at one selling price
and a second PO item "B" gets a **May** purchase at a price **40% higher**. Since the
export renders one row per PO item, exporting a window that spans both months shows
the product twice, at two different selling prices.

To see it:

```
GET /api/v1/inventories/1/export/inventory-in-out?start_date=2026-04-01&end_date=2026-05-31
```

Products 1–5 each appear as two rows — the April "Đơn giá bán" and the +40% May price.
(Underlying values are randomized per run; only the ×1.4 A→B relationship is fixed.)

## Verify it's valid

```sql
-- all four must be 0
WITH lot AS (SELECT inventory_item_id, sum(quantity) q, sum(consumed_quantity) c
  FROM inventory_transactions WHERE transaction_type IN ('purchase','transfer_in') GROUP BY 1)
SELECT
 (SELECT count(*) FROM inventory_items ii JOIN lot l ON l.inventory_item_id=ii.id
    WHERE ii.quantity <> (l.q - l.c))                                              AS onhand_mismatch,
 (SELECT count(*) FROM inventory_transactions
    WHERE transaction_type='purchase' AND consumed_quantity > quantity)            AS over_consumed,
 (SELECT count(*) FROM inventory_items WHERE quantity < 0)                         AS negative_onhand,
 (SELECT count(*) FROM inventory_transactions
    WHERE transaction_type IN ('sell','disposal') AND counter_transaction_id IS NULL) AS unlinked_consumes;
```

```bash
TOKEN=$(make token | grep -E '^eyJ')      # mints a token for the seeded admin test@cim.local
curl -s -H "Authorization: Bearer $TOKEN" \

```

## Reset

```bash
docker compose down -v && docker compose up -d postgres pgweb   # wipe + fresh DB
# then repeat steps 2–4
```
